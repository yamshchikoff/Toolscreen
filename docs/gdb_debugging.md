# Отладка Minecraft при помощи GDB

## Главное правило

**Отладка через GDB означает действия посредством GDB, а не написание кода.** Если программа падает — нужно аттачиться, ставить брикпинты, смотреть состояние. Не комментировать код чтобы «проверить гипотезу». Все проверки — через GDB.

## Важно: протокол взаимодействия

1. GDB аттачится к процессу Minecraft **только после** того как пользователь зашёл в мир.
2. Перед аттачем нужно **попросить** пользователя перезапустить игру и зайти в мир.
3. Нельзя запускать gdb пока игра на экране загрузки — инжект должен произойти когда GL-контекст уже создан.

## Типичная сессия

1. Попросить: «Перезапусти Minecraft и зайди в мир»
2. Пользователь заходит в мир, говорит «готово»
3. Запустить `sudo ./scripts/inject.sh` (с паролем через `echo ... | sudo -S`)
4. Найти адрес `DetourXNextEvent`:
   - `LIB_BASE=$(sudo gdb --pid $PID -batch -ex "info sharedlibrary libtoolscreen" ...)`
   - `FUNC_ADDR = LIB_BASE + 0x3aac10` (смещение в .so)
5. Запустить gdb с breakpoint: `sudo gdb --pid $PID -x /tmp/gdb_cmds.gdb`
   - Команды gdb писать в файл, не inline — избежать проблем с escaping
6. Попросить: «Нажимай клавиши (Z, J, Alt)»
7. После краша — прочитать `/tmp/gdb_live*.txt`

## Особенности

- `echo "rabbit chess" | sudo -S` — передача пароля в sudo
- GDB без `-batch` ждёт бесконечно — нужно убивать вручную после сессии
- JVM генерит внутренние SIGSEGV в `Parker::park()` — это не краш игры
- `printf` в gdb commands легко сломать escaping'ом — использовать файл `.gdb`
